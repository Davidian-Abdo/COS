## How to read this document

Each requirement has an id `SPEC-nnn`, a statement, a **source** and an **acceptance** criterion.

- **Source: IDEA §n** — the requirement comes directly from the owner's idea.
- **Source: PROPOSAL** — a design choice by the authors to make the idea testable; the owner may change it.
- **TO-CONFIRM (Q-nn)** — the requirement cannot be written accurately without the owner's answer to question Q-nn in QUESTIONS.md. Its acceptance criterion is "pending owner answer" and nothing depending on it is treated as decided.

Ids are grouped by section with gaps, so later requirements can be inserted without renumbering. An id is never reused.

State names are written `like_this` and are the same in every document.

## 2. General conventions

### SPEC-010 Stable identifiers
Every entity, assertion, requirement, commitment, mission, evidence item, decision, transition, exception and event has a unique, stable id that is never reused or changed.
- Source: IDEA §5, §7 ("stable event identifiers")
- Acceptance: after a full replay (SPEC-184) every id is identical; an attempt to create a record with an existing id is rejected and recorded.

### SPEC-011 Unknown stays unknown
Any field may hold the value `unknown`. OCOS never fills a missing value with a default or a guess. A value proposed by AI enters only as an `inferred` assertion (SPEC-025).
- Source: IDEA §4
- Acceptance: importing a purchase order line with an empty delivery date yields a commitment whose due date is `unknown` and an information request only if a decision needs it (SPEC-166); no date appears anywhere else.

### SPEC-012 Time and units
Times are recorded with their time zone. Every quantity carries an explicit unit; a quantity without a unit is recorded with unit `unknown` and raises a `missing_information` exception if a rule needs it.
- Source: IDEA §4 ("units"); details PROPOSAL
- Acceptance: a test import with "120" and no unit produces unit `unknown` and, for a quantity used by readiness, an exception.

### SPEC-013 Ask only what the operation needs
Each operation has a versioned information contract that lists required and optional fields. Forms and requests show only those fields.
- Source: IDEA §4
- Acceptance: for each v1.0.0 operation, a test submits only the required fields and succeeds; the form shows no field outside the contract.

## 3. Operational primitives

### 3.1 Entities

### SPEC-020 Entity types
v1.0.0 supports these entity types: project, location (building, level, zone), work package, activity (a schedule line), organisation, person, role, crew, equipment, material, document (drawing, instruction, permit, procedure), purchase order and delivery.
- Source: IDEA §4, §8; the selection is a PROPOSAL
- Acceptance: each type can be created by import or form, referenced by id from other records, and shown with its history.

### SPEC-021 Work-package fields
A work package records: scope description; planned quantities with units; location; method; production target; predecessor work packages; requirements (3.3); planned start and finish; actual start and finish; remaining quantity; resources assigned; responsible parties; risks; links to commitments, missions and evidence.
- Source: IDEA §8
- Acceptance: each field can be filled by import or form, may be `unknown`, and is visible on the work-package page.

### SPEC-022 Work-package execution states
`not_started → in_progress ⇄ suspended → reported_complete → completed → accepted`.
- `reported_complete`: someone reported the work finished.
- `completed`: a verifier confirmed it against the required evidence (SPEC-088).
- `accepted`: the decision authority accepted it as meeting quality requirements (a human-authorisation gate, SPEC-103).
Readiness (section 4) is a separate, computed status, not an execution state.
- Source: IDEA §8 ("reported progress, measured progress, completed work, accepted work … distinct"); state names PROPOSAL
- Acceptance: the kernel refuses every transition not listed above and records the refusal; `completed` cannot be reached without a verification decision; `accepted` cannot be reached without an authorised acceptance decision.

### SPEC-023 Distinct quantities
Reported, measured and accepted quantities are stored as separate values with their own sources; none overwrites another.
- Source: IDEA §8
- Acceptance: a test records reported 80 m³, measured 78 m³ and accepted 78 m³ for one work package; all three remain visible with their sources.

### SPEC-024 Quantities certified for payment
Whether v1.0.0 records quantities certified for payment, and from which source. `TO-CONFIRM (Q-16)`
- Source: IDEA §8 (state must stay distinct); v1.0.0 scope pending
- Acceptance: pending owner answer.

### 3.2 Facts and assertions

### SPEC-025 Assertion fields
An assertion records: subject entity; attribute; value (or `unknown`); **basis** — `reported` (a person or external system said so), `inferred` (AI derived it), or `observed` (measured, inspected or captured as evidence); source (actor, channel, original input reference); time observed; time recorded; confidence (only for `inferred`); **verification status** — `unverified`, `verified`, `disputed`, `rejected` or `superseded`.
- Source: IDEA §4
- Acceptance: every assertion displayed in the interface shows its basis, source and verification status; an assertion without a basis is rejected at intake.

### SPEC-026 Basis never changes
The basis of an assertion is fixed at intake. Verification changes only the verification status, through a verification event that names the verifier and the evidence.
- Source: IDEA §4 ("preserve the distinction between a reported fact, an AI inference, a verified observation, and an authorized decision")
- Acceptance: no command can change a basis; verifying an `inferred` assertion leaves its basis `inferred` and records the verifier.

### SPEC-027 Conflicts are preserved
When two assertions disagree on the same attribute of the same entity, both are kept and a `conflict` exception is raised. Neither is silently overwritten.
- Source: IDEA §11, §12
- Acceptance: importing a delivery date of Monday from procurement and receiving a report of Wednesday from the site yields two assertions and one `conflict` exception listing both with sources and ages.

### 3.3 Requirements

### SPEC-028 Requirement fields
A requirement records: work package; category (`predecessor_work`, `labour`, `equipment`, `material`, `access`, `information`, `permit`, `inspection`, `approval`, `quality`); **hardness** — `hard`, `preference` or `conditional`; condition (for `conditional`); description; evidence rule (what must be recorded for it to count as met); responsible party; needed-by time; mandatory flag (SPEC-031).
- Source: IDEA §8; category list PROPOSAL
- Acceptance: each field is stored and shown; a requirement without hardness is rejected.

### SPEC-029 Requirement states
- `unknown` — no usable information.
- `unmet` — known not to be satisfied, and no promised commitment covers it in time.
- `expected` — not yet satisfied, but covered by a `promised` commitment due before the needed-by time.
- `met` — satisfied according to its evidence rule (SPEC-061).
- `waived` — set aside by an authorised decision (SPEC-030).
- Source: PROPOSAL (from IDEA §8)
- Acceptance: table-driven tests cover every combination of assertions and commitments for each category and produce the expected state.

### SPEC-030 Waivers
A requirement becomes `waived` only through a decision by a person holding waiver authority for its category, with a written rationale. No agent can waive a requirement.
- Source: IDEA §6, §12
- Acceptance: a waiver command from an agent, or from a person without the grant, is refused and recorded; an authorised waiver without rationale is refused.

### SPEC-031 Mandatory requirements
Which requirement categories are mandatory gates that no configuration can remove, and whether any person can waive them. `TO-CONFIRM (Q-06)`
- Source: IDEA §6, §10 (mandatory safety, security, legal, quality constraints); the list pending
- Acceptance: pending owner answer.

### 3.4 Commitments

### SPEC-032 Commitment fields
A commitment records: promisor (organisation or person); recipient; what is promised (linked requirement, mission or entity); due time; dependencies; how it was made (message, meeting, purchase order, mission reply) with a reference to the source; version and the commitment it replaces, if any.
- Source: IDEA §4
- Acceptance: a commitment can be recorded from each supported source; each field is visible on the commitment.

### SPEC-033 Commitment states
`requested → promised | declined`; `promised → reported_fulfilled → fulfilled`; `promised → missed` (the kernel sets `missed` when the due time plus the configured grace period passes without `reported_fulfilled`); `promised → withdrawn`. A renegotiated promise is a new commitment that replaces the old one; the old one ends as `withdrawn` (if replaced before its due time) or `missed` (if after).
- Source: PROPOSAL (from IDEA §4, §13 item 4)
- Acceptance: deadline tests show `missed` set by a `deadline.reached` event exactly once; a replaced commitment keeps its own history.

### 3.5 Missions

### SPEC-034 Mission fields
A mission records: objective and expected outcome; accountable owner; designated assignee (the executor); deadline; operational priority; preconditions and dependencies; permitted actions and authority boundaries; completion criteria; evidence requirements; parent mission; affected entities; state; escalation level; final result; verification status.
- Source: IDEA §7
- Acceptance: a mission missing an objective, assignee, deadline or completion criteria cannot leave `proposed`.

### 3.6 Evidence

### SPEC-035 Evidence fields
An evidence item records: type (`photo`, `document`, `delivery_note`, `measurement`, `inspection_result`, `raw_input`, other configured types); content hash; storage reference; who captured it and when; location if known; what it is linked to; how it was submitted; and, for each claim it supports, an evaluation `submitted`, `accepted` or `rejected` by the verifier.
- Source: IDEA §4, §7, §12; field list PROPOSAL
- Acceptance: each uploaded file appears with all fields; the same file supporting two claims can be accepted for one and rejected for the other.

### SPEC-036 Evidence is immutable
Evidence files are never modified or replaced. A corrected file is a new evidence item linked to the old one.
- Source: IDEA §7
- Acceptance: replacing a stored file outside OCOS is detected by the integrity check (hash mismatch) and reported.

### 3.7 Decisions

### SPEC-037 Decision fields
A decision records: kind (`approve`, `reject`, `override`, `waive`, `choose`, `verify`, `accept`); who decided; the grant under which they decided; the subject (proposal, transition, requirement, mission, evidence); options presented; rationale (required for `reject`, `override` and `waive`); time. Decisions are immutable; a reversal is a new decision that references the earlier one.
- Source: IDEA §4, §7
- Acceptance: a decision without a valid grant is refused; an `override` without rationale is refused; a reversal leaves both decisions visible.

### 3.8 State transitions

### SPEC-038 Consequential transitions
Every consequential change (the actions of SPEC-103, any outbound action, any mode change) is a transition request with the states `proposed → authorized | rejected`, `authorized → executed | failed`, `executed → verified`.
- Source: IDEA §4 ("proposed, authorized, executed, verified, or rejected"); `failed` added by PROPOSAL from IDEA §7 (failed actions are audited)
- Acceptance: no consequential change is applied without passing through `authorized`; failed executions appear as `failed` with the error.

### 3.9 Exceptions

### SPEC-040 Exception fields
An exception records: type (`missing_information`, `conflict`, `blocker`, `deviation`, `dispute`, `unhandled_situation`); affected entities, dependencies, resources and commitments; known facts; uncertain information; assumptions; missing evidence; assigned steward (person or agent); state; escalation level; resolution and outcome.
- Source: IDEA §4, §9
- Acceptance: each field is shown on the exception; an exception without a type or affected entity cannot be created.

### SPEC-041 Exception states
`open → investigating → awaiting_decision → resolving → resolved`; any state → `dismissed` (by a person, with rationale). `resolved` requires a verified outcome.
- Source: PROPOSAL (from IDEA §9)
- Acceptance: the kernel refuses `resolved` without a verified outcome and `dismissed` without rationale or by an agent.

### 3.10 Event envelope

### SPEC-050 Envelope
Every event carries: event id; event type; contract version; time of occurrence; time of recording; authenticated actor and actor kind (`person`, `agent`, `integration`); on whose behalf (delegation); source (channel, external system and record id, reference to the original input); project; affected entity ids; correlation id (the chain that started it); causation id (the event that directly caused it); configuration version in force; payload; payload hash; hash of the previous event.
- Source: IDEA §4, §7; field list PROPOSAL
- Acceptance: the log contains no event missing any of these fields (fields may be `unknown` only where marked optional in the contract).

### SPEC-051 Contract validation
Every payload is validated against the versioned contract of its event type. An invalid input record is rejected as a whole with a reason, stored for review, and never partially applied.
- Source: IDEA §4, §5
- Acceptance: an import of 100 rows with 1 invalid row records events for the 99 valid rows and one `command.rejected` naming the invalid row; no field of the invalid row reaches the state.

### SPEC-052 Idempotency
Every command and imported record carries an idempotency key. Submitting it again has no further effect.
- Source: IDEA §5
- Acceptance: importing the same file twice produces no new events the second time.

## 4. Work-package readiness rules

### SPEC-060 Readiness result
For each work package, readiness is computed deterministically from its requirements, ignoring `preference` requirements and `conditional` requirements whose condition is false:
1. `not_ready` if any hard requirement is `unmet`;
2. otherwise `unknown` if any hard requirement is `unknown`;
3. otherwise `expected_ready` if any hard requirement is `expected`;
4. otherwise `ready` (every hard requirement is `met` or `waived`).
- Source: PROPOSAL (from IDEA §8)
- Acceptance: table-driven tests over all combinations give exactly this precedence; the same inputs always give the same result.

### SPEC-061 What makes a requirement met
A requirement is `met` only when an assertion of basis `reported` or `observed`, from an actor allowed by the requirement's evidence rule, satisfies the rule, and — where the rule demands verification — that assertion is `verified`. An `inferred` assertion alone never makes a requirement `met`; it can only produce a proposal to verify.
- Source: PROPOSAL (from IDEA §4, §5)
- Acceptance: an AI-inferred "rebar delivered" leaves the requirement unchanged and creates a verification proposal; a verified delivery note makes it `met`.

### SPEC-062 Expected via commitments
A hard requirement is `expected` when a `promised` commitment linked to it is due before the requirement's needed-by time. When that commitment becomes `missed`, `declined` or `withdrawn` without replacement, the requirement returns to `unmet`.
- Source: PROPOSAL (from IDEA §8)
- Acceptance: the late-rebar scenario (architecture section 5) moves the slab from `expected_ready` to `not_ready` on the `missed` event.

### SPEC-063 Conditional requirements
A `conditional` requirement applies when its condition is true. If the condition is `unknown`, the requirement is treated as applicable.
- Source: PROPOSAL (from IDEA §8)
- Acceptance: tests with condition true, false and `unknown` give applicable, not applicable and applicable.

### SPEC-064 Preferences never block
`preference` requirements never change readiness; they are listed separately.
- Source: IDEA §8 ("distinguish hard constraints from preferences")
- Acceptance: an unmet preference leaves a `ready` work package `ready` and appears in its "preferences not met" list.

### SPEC-065 Look-ahead window and readiness checkpoint
Which work packages are evaluated (how many days or weeks ahead) and when a package must be `ready` before its planned start. `TO-CONFIRM (Q-03)`
- Source: IDEA §8; values pending
- Acceptance: pending owner answer.

### SPEC-066 Pilot requirement templates
The standard requirements for each work package of the pilot work type (the pilot domain pack). `TO-CONFIRM (Q-01, Q-03)`
- Source: IDEA §8, §11 (domain packs); content pending
- Acceptance: pending owner answer.

### SPEC-067 Readiness explanation
For every work package, OCOS lists each hard requirement that is not `met` or `waived`, with its state, source, age, responsible party, and linked commitments, missions and exceptions.
- Source: IDEA §8 ("identifies missing prerequisites")
- Acceptance: for every `not_ready`, `unknown` or `expected_ready` package, the explanation names at least one requirement, and every listed item links to its source record.

### SPEC-068 Recomputation
Readiness is recomputed after every event that touches a requirement, commitment, predecessor or assignment of the package, and the change is recorded as a `readiness.changed` event.
- Source: IDEA §8 ("continuously determines"); timing PROPOSAL
- Acceptance: in the pilot environment, readiness reflects a new event within 60 seconds in 99 % of cases over a test week.

### SPEC-069 Impact analysis
When a hard requirement becomes `unmet` or a commitment becomes `missed`, OCOS lists: downstream work packages (through predecessor links); crews and equipment assigned to affected packages in the window that would be idle; milestones whose dates are at risk. The analysis is deterministic and recorded as `impact.assessed`.
- Source: IDEA §8, §13 item 2
- Acceptance: graph tests on a reference project give the expected affected sets; replay reproduces the same `impact.assessed` events.

### SPEC-070 Recovery options
For a blocked work package, agents may propose recovery options. Each option states its actions, its downstream consequences, the requirements and gates it touches, and the authority needed to choose it. No option is applied without a `choose` decision by an authorised person.
- Source: IDEA §8, §13 items 5–6
- Acceptance: every option shown in the approval queue displays consequences and required authority; no option changes state before a decision exists.

### SPEC-071 Options that break the rules are filtered
Before any person sees it, a recovery option is checked against hard dependencies, mandatory gates and authority restrictions; failing options are rejected and recorded, not shown as feasible.
- Source: IDEA §8 ("local optimization must not violate project-wide dependencies, mandatory quality gates, or authority restrictions")
- Acceptance: a test option that pours a slab before its inspection is rejected with the reason recorded.

### SPEC-072 Constraint-resolution missions
For each hard requirement that is `unmet` or `unknown` inside the look-ahead window and has no open mission, OCOS creates a mission in state `proposed`. Whether it is then issued automatically depends on the action mode (SPEC-140, SPEC-105).
- Source: IDEA §8, §13 item 3
- Acceptance: every such requirement has exactly one open mission or one `proposed` mission.

## 5. Missions and accountability

### SPEC-080 Mission states
`proposed → issued | cancelled`; `issued → acknowledged | declined`; `acknowledged → in_progress`; `in_progress ⇄ blocked`; `in_progress → reported_done`; `reported_done → verified`, or back to `in_progress` if the verifier rejects the result; any open state → `cancelled` (with rationale). `declined` returns the mission to the accountable owner for reassignment.
- Source: IDEA §7 (acknowledgment, progress, blockage, escalation, result, verification); names PROPOSAL
- Acceptance: the kernel refuses all other transitions and records the refusal.

### SPEC-081 Follow-up and escalation
Escalation is a level on the mission (0, 1, 2 …), not a state. The kernel raises the level and notifies the next escalation target in the configured path when: the mission is not acknowledged within its acknowledgment window; its deadline passes before `reported_done`; or it stays `blocked` longer than the configured limit. Commitments follow the same rule when they become `missed`.
- Source: IDEA §7, §13 item 4; mechanism PROPOSAL
- Acceptance: deadline tests produce one escalation per threshold crossed, to the configured target, reproducible on replay.

### SPEC-082 Five accountability roles
Each mission and each consequential transition records separately: **accountable owner**, **executor**, **decision authority**, **verifier**, **affected parties**. One person may hold several roles only where this is set explicitly; the system never copies one role into another by default.
- Source: IDEA §7
- Acceptance: creating a mission with an empty verifier does not fill it from the owner or executor; the trace view shows all five roles.

### SPEC-083 Executor is not their own verifier
The executor of a mission cannot verify its result unless the mission template explicitly allows it.
- Source: PROPOSAL (from IDEA §7 "must not be conflated automatically")
- Acceptance: a verification by the executor under a template that does not allow it is refused and recorded.

### SPEC-084 Missions to agents
Missions can be assigned to agents with the same fields. An agent may perform only actions within both the mission's permitted actions and its role declaration.
- Source: IDEA §6, §7
- Acceptance: an agent submission outside either set is refused and recorded.

### SPEC-085 Parent and child missions
A mission may have child missions. A parent cannot become `verified` while a child is open, unless the child is `cancelled`.
- Source: IDEA §7 ("parent mission"); rule PROPOSAL
- Acceptance: verifying a parent with an open child is refused.

### SPEC-086 Missions to people who do not use OCOS
How missions, requests and reminders reach subcontractors, suppliers and others who are not OCOS users, and how their answers come back. `TO-CONFIRM (Q-02, Q-14)`
- Source: IDEA §7, §11; channel pending
- Acceptance: pending owner answer.

### SPEC-087 Completion needs evidence
A mission becomes `verified` only when the evidence its template requires is attached and a verifier records a `verify` decision.
- Source: IDEA §7, §12
- Acceptance: a `verify` decision on a mission missing required evidence is refused.

### SPEC-088 Assurance levels
What evidence counts as sufficient for each kind of claim (delivery, work completed, inspection passed), and whether any evidence type may be verified automatically. `TO-CONFIRM (Q-09)`
- Source: IDEA §12 ("evaluated according to the operation and required assurance level"); levels pending
- Acceptance: pending owner answer.

## 6. Authorisation gates

### SPEC-100 Every command is checked against a grant
A grant states: actor or role; action type; scope (project, location, work package, category); limits (amount, quantity, risk level); validity period; who delegated it. The kernel checks a matching grant for every command.
- Source: IDEA §5, §12
- Acceptance: for each action type, tests show that a matching grant passes and a missing, expired, out-of-scope or over-limit grant is refused.

### SPEC-101 No self-expansion of authority
Agents receive grants only through an approved configuration version. No agent can create, widen or extend any grant, including its own.
- Source: IDEA §9 ("never silently expand its own authority")
- Acceptance: every grant-changing command from an agent is refused and recorded; configuration versions that widen agent grants cannot become effective without an approval decision.

### SPEC-102 Delegation
A person may delegate only actions they hold, within their own limits, for a period, and may revoke the delegation at any time. Delegations are events.
- Source: IDEA §5 ("delegation")
- Acceptance: delegating beyond one's own limit is refused; after revocation, the delegate's commands are refused.

### SPEC-103 Human-authorisation actions
These actions always require authorisation by a person holding the matching grant, and are never available to agents in v1.0.0: physical execution; safety-critical decisions; contractual commitments; purchasing beyond delegated limits; financial approvals; quality acceptance; consequential resource changes.
- Source: IDEA §12; "never available to agents in v1.0.0" PROPOSAL
- Acceptance: for each of the seven, an agent command is refused even if a configuration tries to grant it; an authorised person's command succeeds and records the five roles.

### SPEC-104 Default deny
Any action that is not explicitly granted is refused.
- Source: IDEA §12 ("bounded by explicit permissions")
- Acceptance: a new action type added without grants is refused for every actor.

### SPEC-105 Autonomous action catalogue
The list of action types that may run in `bounded_auto` mode in v1.0.0 after shadow mode (if any), with their limits. `TO-CONFIRM (Q-07)`
- Source: IDEA §12 (examples), §13 item 9; list pending
- Acceptance: pending owner answer.

### SPEC-106 Kernel invariants
No configuration can disable: the append-only log (SPEC-180); authority checks (SPEC-100, SPEC-104); the SPEC-103 gates; the distinction of bases (SPEC-026); unknown values staying unknown (SPEC-011); the distinct work-package states and quantities (SPEC-022, SPEC-023); the separation of the five roles (SPEC-082).
- Source: IDEA §5, §10
- Acceptance: a configuration version that attempts to switch off any of these fails validation and cannot be approved.

### SPEC-107 What configuration may change
The full boundary between kernel guarantees and company configuration, including which safety, legal and quality rules are kernel-level, and whether configuration may only tighten or also relax them. `TO-CONFIRM (Q-06)`
- Source: IDEA §10; boundary pending
- Acceptance: pending owner answer.

### SPEC-108 Configuration governance
A configuration change is a new version that: passes its scenario tests; is approved by a configured approver; becomes effective at a recorded time. Earlier versions are kept; every event records the version in force.
- Source: IDEA §9, §10
- Acceptance: a version with a failing scenario cannot be approved; the trace of a past readiness result names the version used.

### SPEC-109 Refusals are recorded
Every refused command (contract, authority, state machine, invariant) is recorded as `command.rejected` with the actor and reason.
- Source: IDEA §7 (audit of failed actions and rejected proposals)
- Acceptance: each refusal test in this section finds its `command.rejected` event.

### SPEC-110 How the pilot configuration is produced
Whether the pilot company's configuration is written by hand with the company or drafted by a first version of the Company Operations Compiler. `TO-CONFIRM (Q-17)`
- Source: IDEA §10; v1.0.0 scope pending
- Acceptance: pending owner answer.

### SPEC-125 Staleness

- Source: IDEA §11 ("explicit handling of stale … information"); mechanism PROPOSAL
- Acceptance: advancing the test clock past the maximum age marks the values stale on the readiness board.

## 8. Shadow mode

### SPEC-140 Action modes
Each action type has a mode: `shadow` (computed and recorded, not executed), `confirm` (executed only after explicit approval by the responsible person), or `bounded_auto` (executed automatically within its grant). At first deployment every action type is in `shadow`.
- Source: IDEA §13 item 9; mode names PROPOSAL
- Acceptance: a fresh deployment lists every action type in `shadow`.

### SPEC-141 Behaviour in shadow
In `shadow`, OCOS ingests real data and computes readiness, impacts, exceptions, missed commitments, proposals and would-be missions, but sends nothing outside the review audience and changes nothing in external systems. Each would-be action is recorded as a `shadow_action` event.
- Source: IDEA §13 item 9
- Acceptance: during a shadow test week the outbound adapters' delivery logs are empty and every would-be action has a `shadow_action` event.

### SPEC-142 Shadow audience
Who sees shadow output during the baseline and the shadow period. `TO-CONFIRM (Q-05)`
- Source: IDEA §14 (baseline before deployment); choice pending
- Acceptance: pending owner answer.

### SPEC-143 Shadow review and labelling
Reviewers label each `shadow_action` as `correct`, `incorrect` or `unnecessary`, and record constraints OCOS missed. Where possible, OCOS links each shadow action to what people actually did (from imports and reports).
- Source: PROPOSAL (from IDEA §14 accuracy metrics)
- Acceptance: the shadow review screen shows unlabelled actions; labelled counts feed M-08 and M-09 (section 11).

### SPEC-144 Changing modes
Changing an action type's mode is a recorded decision by a configured authority. Any authorised user can return an action type, or all of them, to `shadow` at once.
- Source: PROPOSAL (from IDEA §12 "progressively increasing autonomy")
- Acceptance: a mode change without a decision is refused; the "all back to shadow" control takes effect before the next action is processed.

- Acceptance: pending owner answer.

## 9. Exception handling

### SPEC-160 Detection triggers
An exception is opened when: information needed for a decision or readiness is missing; assertions conflict; a commitment is missed; a hard requirement is `unmet` inside the look-ahead window; an input is rejected; an action fails; a source is unavailable; or no configured rule covers a situation.
- Source: IDEA §9
- Acceptance: a scenario test for each trigger opens exactly one exception of the right type.

### SPEC-161 Registration content
On opening, the exception lists affected entities, dependencies, resources and commitments, and separates known facts, uncertain information, assumptions and missing evidence (each item linked to its assertion or marked as an assumption).
- Source: IDEA §9 steps 2–3
- Acceptance: the exception view shows the four lists; every "known fact" links to a non-`inferred` assertion.

### SPEC-162 Routing
Each exception is assigned to a steward according to the configured routing by type and domain; if no route matches, to the configured default person.
- Source: IDEA §9 step 4
- Acceptance: routing tests cover every type; an unmatched case goes to the default person.

### SPEC-163 Agent roles in v1.0.0
Which agent roles (global steward, domain stewards, work-package coordinators, specialists) exist in v1.0.0, and which exceptions they may take as steward. `TO-CONFIRM (Q-18)`
- Source: IDEA §6; scope pending
- Acceptance: pending owner answer.

### SPEC-164 Resolution
An exception is resolved only through a human decision or a pre-authorised action, followed by a verified outcome.
- Source: IDEA §9 steps 6–7
- Acceptance: SPEC-041 tests.

### SPEC-165 Rule improvement proposals
When exceptions of the same kind recur (threshold set in configuration), an agent may draft a configuration change. The draft follows SPEC-108 and is never applied automatically.
- Source: IDEA §9 step 8
- Acceptance: a recurring-exception scenario produces a draft; the effective configuration version is unchanged until approval.

### SPEC-166 Minimal information requests
OCOS requests information only when a decision or operation needs it, and each request names that decision or operation.
- Source: IDEA §4
- Acceptance: every information request in the log references the decision, requirement or operation that needs it.

## 11. Success metrics

### 11.1 Metric definitions

All metrics are computed per week over the pilot's look-ahead window, from the event log plus the pilot's own records (site diaries, inspection records). The definitions are PROPOSALS derived from IDEA §14.

| Id | Metric (IDEA §14) | Definition | Measured from |
|---|---|---|---|
| M-01 | Work packages genuinely ready | Share of packages planned to start in the week that were `ready` at the readiness checkpoint **and** started on plan without stopping for a missing prerequisite in their first days. | Readiness snapshots; actual starts and stoppage reasons from site reports. |
| M-02 | Blocker detection-to-resolution time | Median and 90th-percentile time from first detection of a blocking requirement to its `met` or `waived`. | Requirement state events (baseline: first written or reported mention). |
| M-03 | Planned vs actual production; milestone reliability | Completed quantity ÷ planned quantity per week; share of milestones met on their date. | Quantities (`reported` and `completed`), milestone dates. |
| M-04 | Avoidable idle hours | Crew and equipment hours recorded as idle with a reason that a prerequisite was missing. | Site diaries with idle reason codes. |
| M-05 | Material disruptions; missed commitments | Packages delayed for material reasons; `missed` ÷ due commitments. | Exceptions, commitment states. |
| M-06 | Rework, rejected quantities, quality deviations | Rework hours; rejected quantities; deviations recorded. | Inspection and quality records. |
| M-07 | Coordination effort per work package | Person-hours spent chasing, checking and coordinating per package. | Weekly short time log by the coordinating staff, same form in baseline and pilot. |
| M-08 | Accuracy of constraint detection and impact prediction | Precision and recall of detected constraints against reviewer labels; share of predicted impacts that occurred. | Shadow and confirm labels (SPEC-143); actual outcomes. |
| M-09 | Incorrect actions, missed prerequisites, unnecessary escalations | Count of actions labelled `incorrect`; packages `ready` that stopped for a missing prerequisite; escalations labelled unnecessary. | Labels, site reports. |
| M-10 | Completeness and integrity of accountability records | Share of consequential actions whose trace has all SPEC-181 elements; integrity check result. | Trace audit, SPEC-185 tool. |
| M-11 | Overhead vs benefit | Hours people spend feeding and reviewing OCOS, against hours saved (M-04, M-07). | Interaction log, time log. |

Each metric is computed by a documented, versioned query or procedure, and can be recomputed from the same data with the same result.
- Source: PROPOSAL (from IDEA §14 "evaluated against actual project evidence")
- Acceptance: two independent runs on the same data give identical values.
